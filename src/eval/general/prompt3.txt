## Hypothesis-Driven Research Workflow
Before implementing a training method, first propose concrete hypotheses about what may improve performance on {benchmark}. Then verify or falsify those hypotheses with targeted experiments.

For each major iteration:
1. State the hypothesis.
2. Explain why the hypothesis is plausible for {benchmark}.
3. Define a small verification experiment, preferably using \`evaluate.py --limit\` for fast feedback.
4. Run the experiment or inspect the relevant evidence.
5. Record whether the result supports or rejects the hypothesis.
6. Decide the next method based on the evidence.

Do not make large, expensive changes without first formulating a hypothesis and a verification plan. Keep a concise experiment log in the current directory so that your reasoning, data choices, training commands, and model selection are auditable.

## Optional Codex Skill Workflow
You may use the following two Codex skill guides as local operating patterns when they help your research workflow. These are not a reason to delay training, and they do not override the benchmark rules below.

### skill-creator
Use this when creating a reusable local workflow, checklist, script bundle, or domain-specific guide would make your experiments more reliable.

A local skill is a folder with a required `SKILL.md` file and optional bundled resources:

```text
skills/<skill-name>/
|-- SKILL.md
|-- scripts/
|-- references/
`-- assets/
```

`SKILL.md` must start with YAML frontmatter:

```markdown
---
name: <skill-name>
description: <clear trigger condition for when to use this skill>
---
```

Guidelines:
- Keep the skill concise. Include only task-specific knowledge, workflows, or commands that you will actually reuse.
- Put deterministic or repeatedly used code in `scripts/`.
- Put longer benchmark notes, schemas, or examples in `references/` and read them only when needed.
- Do not create extra docs like README, installation guides, or changelogs unless they directly help the current job.
- Prefer local, auditable scripts over fragile one-off shell commands when the same experiment will be repeated.

### skill-installer
Use this only if an existing Codex skill would materially speed up the job. Installed skills must be local to this run and must not require privileged operations.

Based on your prior experience, you may proactively identify and install relevant skills that are likely to improve the research, training, evaluation, or debugging workflow for this benchmark.

If you install skills, install them under the current working directory:

```bash
mkdir -p "$PWD/.codex/skills"
export CODEX_HOME="$PWD/.codex"
```

Curated public skills normally come from:

```text
https://github.com/openai/skills/tree/main/skills/.curated
```

Experimental skills normally come from:

```text

```

You may use `git`, `curl`, or `wget` to fetch a public skill into `$CODEX_HOME/skills/<skill-name>` if network access works. If network access fails or installation takes too long, skip it and continue with the training pipeline. Do not install into global system directories, do not use `sudo`, and do not make `final_model` depend on any installed skill.

Important limitations:
- The currently running agent process may not hot-load newly installed skills. Treat installed or created skills as local reusable instructions and scripts unless you explicitly launch a new Codex process with `CODEX_HOME="$PWD/.codex"`.
- Creating or installing skills is optional. The priority is still to improve and submit `final_model`.
- Keep a short note in your experiment log when you create or install a skill, including why it helped and where it is stored.
